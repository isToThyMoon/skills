# UI 设计入门：从“好看一点”到可执行要求

你要学习的不是一套神秘的审美口诀，而是一种描述与判断界面的语言：指出**什么对象**在**什么场景**下有问题，希望改变**哪个维度**，受哪些条件约束，以及用什么证据判断改好了。

本次暂定范围是网页与 App 的产品界面（UI）：信息组织、布局、视觉层级、交互状态、响应式与可访问性。用户研究、品牌战略、插画、复杂动效和前端实现只标出接口，暂不深入。UI 与 UX 也不完全相同：UI 聚焦人直接看到和操作的界面；UX 还包括完整流程、内容、服务与使用感受。

先建立一条骨架：

> 用户任务约束信息架构；信息架构决定页面放什么、如何分组；交互设计决定怎样操作和反馈；视觉层级帮助用户看懂主次；组件与设计系统保持一致；可用性与可访问性检查结果是否真的有效。

“好看”通常是这些关系处理得当后的综合感受，不是一个可直接执行的修改项。

## 一、八类领域地图

### 1. 核心实体：设计到底在操作什么

- **使用者与任务（user / task）**：谁在什么情境下要完成什么事。任务优先级应约束页面的视觉优先级。
- **页面或屏幕（page / screen）**：承载某一阶段任务的整体，由内容、区域和组件组成，不是一张只供观看的海报。
- **内容与信息（content / information）**：标题、说明、数据、图片、提示。真实内容的长度和重要性会改变布局。
- **区域（section / region）**：导航区、表单区、内容区、操作区等。区域用于表达信息分组。
- **组件（component）**：按钮、输入框、卡片、标签、弹窗等可复用单元。
- **状态（state）**：默认、悬停、键盘聚焦、禁用、加载、成功、错误、空数据等情形。状态依附于组件、页面和数据变化。
- **视口与输入方式（viewport / input modality）**：屏幕宽度、方向，以及鼠标、触摸、键盘等输入条件；它们约束布局和操作方式。

### 2. 核心概念：专业判断依靠什么

- **信息架构（information architecture）**：内容如何分类、命名和导航。若结构混乱，改颜色通常解决不了问题。
- **视觉层级（visual hierarchy）**：通过位置、大小、字重、颜色、对比和留白，让人知道先看什么、再看什么。它应表达任务优先级，而不是制造更多焦点。
- **分组与邻近（grouping / proximity）**：距离、容器和分隔帮助人判断哪些内容属于一组；若分组不清，应先检查结构，再决定是否加边框。
- **对齐与栅格（alignment / grid）**：为元素建立共同基准，使关系可预测。栅格是组织手段，不是必须露出来的装饰。
- **排版层级（typographic hierarchy）**：给标题、正文、辅助信息等不同角色稳定的字号、字重和行高。Apple 的排版指南明确将排版用于可读性和信息层级，并提醒文字放大后仍需保持层级。[Apple：Typography](https://developer.apple.com/design/human-interface-guidelines/typography)
- **一致性（consistency）**：相同含义采用相同表现和行为，降低重新学习成本。
- **可供性与操作提示（affordance / signifier）**：让用户看得出哪里能点、输入、拖动或展开。
- **反馈（feedback）**：操作后让用户知道系统正在处理、已经成功或为何失败。
- **响应式/自适应（responsive / adaptive）**：根据屏幕、方向、文字尺寸和内容变化重排，不等于把桌面稿等比例缩小。Apple 建议在不同设备、方向、本地化和文字尺寸下预览布局。[Apple：Layout](https://developer.apple.com/design/human-interface-guidelines/layout)
- **可访问性（accessibility）**：让不同感知、运动、认知能力和输入方式的人都能获取信息并完成操作。

### 3. 常见实用术语：用于检索和沟通

- **CTA（Call to Action）**：希望用户执行的关键动作，如“创建账户”。
- **Primary / secondary action**：主操作与次操作；这是任务优先级，不只是两种按钮颜色。
- **Whitespace / negative space**：留白，用于分组、节奏和聚焦，不等于浪费空间。
- **Visual weight**：视觉重量；大小、颜色、对比、位置等共同决定一个元素有多抢眼。
- **Breakpoint**：布局发生结构变化的宽度条件。
- **Design token**：对颜色、字号、间距、圆角等基础值的命名，供多个组件共享。
- **Design system**：组件、令牌、规则与文档组成的系统，不只是一个组件素材库。
- **Wireframe / mockup / prototype**：依次常指用于检查结构的线框图、表达完整视觉的视觉稿、演示或测试交互的原型；团队用法可能略有差异。
- **Empty / loading / error state**：空、加载、错误状态。只画理想的默认状态通常不足以交付实现。
- **Heuristic evaluation**：依据通用可用性原则检查潜在问题；它不能替代真实用户测试。

### 4. 工作流：专业工作怎样推进

一条常见但非唯一的路径是：

1. 明确使用者、场景、任务和限制，产出页面目标与内容清单。
2. 组织信息和操作路径，产出页面结构或用户流程；若主任务仍不清楚，回到上一步。
3. 用线框图验证顺序、分组与操作，而不是急着选颜色。
4. 用排版、间距、颜色和容器建立视觉层级，形成视觉稿。
5. 整理可复用组件并补齐交互、数据和错误状态。
6. 定义不同屏幕、真实文案和输入方式下的适配规则。
7. 用可用性任务、启发式检查和可访问性标准验收；发现问题后返回相应环节，而非一律“再润色”。

### 5. 常见产物：你可以要求 Agent 交付什么

- **页面目标、内容清单**：确认什么必须出现、什么最重要。
- **用户流程图（user flow）**：检查从入口到完成任务的步骤与分支。
- **线框图**：检查结构、顺序和操作。
- **高保真视觉稿**：检查排版、色彩、间距和品牌表达。
- **交互原型**：检查跳转、反馈和状态转换。
- **组件清单与状态表**：让默认、聚焦、禁用、加载和错误等状态可检查。
- **设计令牌与组件规范**：让重复元素遵守同一规则。
- **响应式规则**：说明不同宽度下哪些元素重排、折叠或滚动。
- **验收清单**：连接设计、实现和最终检查。

### 6. 评价维度：怎样判断好坏

- **任务清晰度**：让一个未参与设计的人看页面数秒，能否说出“这是做什么的”和“下一步在哪里”？
- **层级**：转成灰度或快速眯眼看，前三个焦点是否符合任务优先级？
- **分组与一致性**：相关信息是否明显成组；相同含义的组件是否使用相同样式和行为？
- **可读性**：换成长标题、真实数据、较大文字后，内容是否仍易读且不遮挡？
- **反馈与恢复**：加载、成功、失败是否可见；错误是否说明发生了什么以及如何恢复？
- **适配性**：窄屏、宽屏、不同方向和输入方式下能否完成同一核心任务？
- **可访问性**：键盘能否到达所有操作；焦点是否可见；信息是否不只依赖颜色；对比度等是否符合项目选定的标准？

WCAG 2.2 是 W3C 发布的 Web 可访问性标准，其中包含文本对比、键盘焦点、目标尺寸等可测试的成功准则；采用时仍需明确适用范围和目标等级。[W3C：Understanding WCAG 2.2](https://www.w3.org/WAI/WCAG22/understanding/)

### 7. 常见失败模式：症状不等于原因

| 可见症状 | 候选原因 | 应怎样验证 |
|---|---|---|
| 所有东西都很抢眼 | 任务优先级不清，或颜色、字重、尺寸同时滥用 | 先列主次任务，再看视觉焦点是否匹配 |
| 页面拥挤 | 内容过多、分组不清、密度过高或容器过窄 | 分别检查内容必要性、分组和不同宽度，不能直接诊断为“留白不足” |
| 简洁但不知道怎么用 | 控件过度隐藏、标签不清或反馈缺失 | 请未见过页面的人指出哪里能操作并完成一个任务 |
| 各页单独好看但整体不一致 | 组件规则和令牌缺失 | 对比同类按钮、表单、卡片的结构与状态 |
| 设计稿漂亮，实现后崩坏 | 只使用理想短文案、单一尺寸和默认状态 | 注入长文案、空数据、错误、小屏与文字放大条件 |
| 颜色“高级”但难读 | 低对比被当成精致，也可能受字号和字重影响 | 按选定的 WCAG 条件测量，而不是凭肉眼猜测 |

### 8. 标准与框架：不要把所有指南都叫“行业标准”

- **WCAG 2.2**：W3C 的 Web 可访问性标准，包含可测试成功准则；不是视觉风格手册。
- **Apple Human Interface Guidelines**：Apple 平台的官方设计指南，适合查平台原则、布局、排版和可访问性；不是所有网页的强制规则。[Apple HIG](https://developer.apple.com/design/human-interface-guidelines/)
- **Nielsen 十项可用性启发式**：覆盖系统状态、现实世界语言、用户控制、一致性、防错和错误恢复等通用检查原则；它们是启发式规则，不是具体合规要求。[NN/g：10 Usability Heuristics](https://www.nngroup.com/articles/ten-usability-heuristics/)
- **产品设计系统**：某个组织为自身产品建立的规则。Material Design、Apple HIG 与内部设计系统有不同适用条件，不能混装成一套“最佳实践”。

## 二、贯穿案例：把“注册页做得好看、专业一点”翻译出来

以下是**教学模拟**，不是对真实页面的实测：对象是桌面和手机共用的 SaaS 注册页，流程固定为“邮箱 + 密码 → 创建账户”，允许调整布局、文案和视觉；案例目标明确把邮箱注册作为主路径，Google 注册作为次路径。为演示错误状态，另假设产品规则是“密码至少 8 个字符”。品牌气质、设计系统、目标浏览器和正式合规等级未知，因此不虚构字体、颜色或合规结论。

### 1. 模糊意图

> 把注册页做得好看一点、专业一点。

真正希望改善的结果可能是“用户更容易理解并完成注册”，也可能只是“更符合品牌气质”。两者会导向不同方案，因此不能直接开始加渐变、阴影或插画。

### 2. 先提出待观察问题

- 用户是否看不出页面用途或主操作？可能是视觉层级，也可能是文案问题。
- 字段是否显得散乱？可能是对齐、分组或容器宽度问题。
- 是否出现多个同等抢眼的操作？可能是任务优先级未表达。
- 移动端是否溢出？可能是固定尺寸或内容适配规则缺失。
- 错误后是否无法恢复？可能是错误状态和反馈不完整。

这些目前只是候选解释，不是已经确认的诊断。

### 3. 模拟观察、证据与判断

假设审查现稿后得到以下**模拟观察**：标题只有“欢迎”，大插画隔开标题与表单；“创建账户”和“使用 Google 注册”都是同样醒目的实心按钮；输入标签会在输入后消失；错误只显示红框；固定 640px 的表单在 360px 视口截断；键盘 Tab 时没有可见焦点。

这些证据支持“用途表达不足、操作层级不明、错误反馈依赖颜色、响应式规则与焦点状态缺失”，不支持“配色不高级”或“应该换字体”。因此将标题改为“创建账户”，让标题、说明、表单和主操作连续排列；邮箱注册作为主路径，Google 注册降为次路径；标签移至输入框上方；错误同时显示图标和恢复文字；容器改为可收缩宽度并补齐焦点状态。

### 4. 用领域概念作条件化判断

- 若“创建账户”不是首要焦点，调整视觉层级，而不是默认把按钮做得更大。
- 若字段之间归属不清，先用邻近、对齐和标签改善分组；边框卡片只是一种可选机制。
- 若同类控件样式不同，先建立组件状态和令牌，而不是逐个润色。
- 若移动端遮挡或截断，定义重排和换行规则；不要只缩小整个页面。
- 若键盘焦点不可见或对比不足，按选定的 WCAG 2.2 条件修正。

### 5. 形成产物并验收

上述判断实际形成下面的线框片段：

```text
创建账户
开始使用 Acme 管理你的项目

邮箱
[ name@example.com              ]
密码                       [显示]
[ ••••••••                      ]
[错误图标] 密码至少需要 8 个字符  ← 来自本案例的教学假设

[         创建账户         ]  主操作
----------- 或者 -----------
[      使用 Google 注册     ]  次操作
已经有账户？登录
```

状态表片段也随之产生：输入框获得键盘焦点时显示清晰轮廓；密码错误时保留输入，并同时显示边框、图标和错误文字；提交中按钮显示“正在创建…”并防止重复提交；窄屏下容器收缩并保留页面边距。

再做一次**教学模拟验收**：360px 下不再截断，暂时通过；短密码错误可读且输入被保留，暂时通过；键盘能到达“显示密码”，但其焦点仍不明显，于是返回组件状态补焦点；灰度查看时两个注册按钮仍接近同权重，于是返回视觉层级继续降低次按钮权重。尚未实际测量颜色对比、屏幕阅读器输出或真实用户完成率，所以不能宣称已经合规或提升了注册效果。

下面是自足的可复制说明。它仍是**教学模拟模板**；用于真实页面时，必须先用实际页面复核其中的模拟观察，不能直接把它们当作真实诊断：

> 这是一个教学模拟任务。改进桌面与手机共用的 SaaS 注册页：保留“邮箱 + 密码 → 创建账户”的固定流程，允许调整布局、文案和视觉；将邮箱注册作为主路径、Google 注册作为次路径。示例密码规则为“至少 8 个字符”。
>
> 以下是模拟观察，不是真实诊断：标题只有“欢迎”，大插画打断标题与表单的阅读路径；邮箱和 Google 注册按钮同等醒目；输入标签会在输入后消失；错误只用红框表达；固定 640px 表单在 360px 视口截断；键盘焦点不可见。若用于真实页面，请先逐项复核并记录证据，只修改被实际证据支持的问题。
>
> 对经复核成立的问题：把标题改为明确的注册任务，让标题、说明、表单和主操作形成连续阅读路径；降低 Google 注册的视觉权重；使用持久标签；错误状态同时提供非颜色提示、具体原因和恢复方式；补齐键盘聚焦、提交中、成功与禁用状态；说明桌面和手机宽度下的重排规则。不要虚构字体、配色或用户偏好。
>
> 交付线框图、桌面与移动端视觉方案、组件状态表和验收清单。验收覆盖 360px 窄屏、键盘全流程、长错误文案和文字放大；按项目最终选定的 WCAG 2.2 等级检查相关成功准则。若两个注册路径仍同等抢眼，返回视觉层级；若内容溢出，返回响应式规则；若错误无法恢复，返回状态与反馈。品牌气质、现有设计系统、目标浏览器和合规等级尚未提供，列为待确认项，不自行指定。

这次新增的有效信息不是更多“专业词”，而是：具体对象、期望结果、先检查什么、哪些修改需要证据、交付物、验收方法、失败后的返工位置，以及尚未确认的决策条件。

## 三、后续导航

建议按这条顺序继续：

1. **任务、信息架构、视觉层级**：先学，因为它们决定“什么重要”；结构不清时，风格润色很难救场。
2. **分组、对齐、排版、间距、色彩角色**：学习界面如何表达关系和主次。
3. **组件、状态、反馈、设计系统**：从一张静态图走向可用且一致的产品。
4. **响应式、可用性与可访问性**：学习如何用边界条件和证据验收。
5. **品牌、动效、用户研究**：按目标选读；它们重要，但不是理解基础界面语言的先决条件。

本地图尚未展开色彩理论、字体选择、Figma 操作、用户研究方法、动效和工程实现。下一步最有价值的行动，是选一个具体界面（哪怕是一张你喜欢或不喜欢的截图），实际做一次“观察现象 → 区分候选原因 → 改写要求 → 定义验收”；也可以直接让我展开“视觉层级”，或用一个新情境检验你能否把模糊诉求改写清楚。
