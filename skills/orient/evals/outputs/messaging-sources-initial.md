# 消息队列与可靠消息处理：一张可用于表达需求的领域地图

消息队列解决的不是抽象的“消息别丢”，而是：当生产者、网络、Broker、消费者或下游依赖发生延迟、重试、崩溃时，怎样让工作最终达到可接受的业务状态，并且能发现、解释和恢复异常。

本地图面向初学者，范围是常见的异步业务消息处理：队列、发布/订阅、日志型消息系统，以及生产、消费、重试和运维。暂不深入共识算法、Broker 内核实现、跨地域灾备、流处理计算框架和具体产品选型。先记住这条骨架：

> **业务事实 → 生产者发布 → Broker 持久化/路由 → 消费者处理 → 业务副作用 → 确认或重试 → 监控与恢复**

可靠性是一条端到端链路。Broker 接收成功不等于业务处理成功；“至少一次投递”也不等于副作用只发生一次。Kafka 官方文档特别把发布持久性与消费处理保证拆成两个问题，并指出写入外部系统时，所谓 exactly-once 仍需要目标系统配合。[Kafka：Message Delivery Semantics](https://kafka.apache.org/40/design/design/#message-delivery-semantics)

## 一、八类领域地图

### 1. 核心实体：系统里有哪些角色和对象

- **生产者（producer）**：创建并发布消息。它必须知道何时算“发布成功”，超时后能否安全重试。
- **消息（message / event / command）**：载荷加标识、时间、类型、版本、关联 ID 等元数据。事件描述已经发生的事实；命令请求某方执行动作，两者语义不同。
- **Broker 与目的地（queue / topic / stream）**：接收、保存并路由消息。队列常表示竞争消费；主题常表示一个事实供多个订阅者各自消费；日志型系统还允许按位置重放。
- **分区与消息键（partition / key）**：把流量拆分以扩展吞吐，也定义通常能维持顺序的范围。要求“全局有序”比“同一订单内有序”约束更强、代价也更高。
- **消费者与消费者组**：读取并处理消息。组内成员通常分摊工作，不同订阅/组可各自处理同一事实。
- **业务副作用**：写数据库、扣库存、发送邮件、调用支付等真正改变世界的操作。可靠性最终应检查副作用，而不只检查消费 API 返回成功。
- **确认位置（ack / offset / settlement）**：系统用它记录一次投递或消费走到了哪里。确认相对业务提交的先后顺序，决定崩溃时更可能重复还是丢处理。
- **重试区与死信区（DLQ/DLX）**：承接暂时失败或反复失败的消息。它们是隔离与恢复设施，不是自动解决错误的垃圾桶。

### 2. 核心概念：可靠性靠哪些区分来理解

- **持久性与可用性**：消息是否在进程、节点或存储故障后仍存在，与系统当前是否能接收/交付消息是两件事。复制、落盘和发布确认共同影响生产端的丢失窗口。
- **投递语义**：at-most-once 可能丢但不重投；at-least-once 倾向不漏投但允许重复；exactly-once 必须说明作用范围。AMQP 1.0 规范展示了 settlement 时机如何导出不同投递保证，也明确 at-least-once 可能造成重复处理。[OASIS AMQP 1.0 Transport](https://docs.oasis-open.org/amqp/core/v1.0/amqp-core-transport-v1.0.html#section-message-transfers)
- **确认时机**：先确认后处理，崩溃时可能漏处理；先处理后确认，处理成功但确认前崩溃时会重投。因此 at-least-once 消费通常要与幂等结合。
- **幂等（idempotency）与去重**：同一业务操作被执行多次，最终副作用仍等同于一次。消息 ID 只是输入；还需定义去重键的业务范围、原子写入、保存期限和冲突行为。
- **顺序**：必须说明按什么键、在哪段链路、允许多大乱序。重试、并行消费者和分区扩缩都可能改变观察顺序。
- **背压与流量整形**：生产速度超过消费能力时，积压会增长。限流、批处理、扩容和负载降级是不同选择；盲目重试可能进一步压垮下游。
- **失败分类**：瞬时失败适合退避重试；永久无效消息适合隔离；未知失败需要限制次数并保留诊断上下文。把所有异常无限重试会形成 poison message 循环。
- **一致性边界**：数据库写入和消息发布若不在同一原子边界，会出现“库已写、消息没发”或反向状态。Outbox、事务能力、幂等消费和对账是不同条件下的协调手段，不应无条件叠加。
- **保留与重放**：消息保存多久、能否从某个位置重放、重放是否再次触发外部副作用。重放能力越强，越需要版本兼容和幂等保护。

### 3. 高频术语：用于检索与交流

- **Publish confirm / producer acknowledgement**：Broker 对发布结果的确认；不同于消费者 ack。RabbitMQ 明确把 publisher confirms 与 consumer acknowledgements 视为两个相互独立的数据安全机制。[RabbitMQ confirms](https://www.rabbitmq.com/docs/confirms)
- **Ack / nack / reject**：消费者表示成功接受、失败或拒绝一次投递；其后是重入队、丢弃还是进死信取决于配置与系统。
- **Consumer offset**：日志型系统中消费者已提交的位置，不等同于业务副作用必然成功。
- **Visibility timeout**：消息被消费者取得后暂时不对其他消费者可见；超时未删除/确认会再出现。SQS 官方说明即使在可见性超时内，at-least-once 模型仍不能绝对保证不重复投递。[SQS visibility timeout](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-visibility-timeout.html)
- **Retry / backoff / jitter**：重试、退避、随机抖动；用于减少短暂故障和同步重试风暴。
- **Poison message**：持续无法成功处理的消息，会阻塞顺序或制造重试循环。
- **Dead-letter queue (DLQ)**：隔离多次失败、过期或被拒消息的目的地；必须配套告警、检查和重放流程。
- **Consumer lag / queue depth / oldest age**：消费落后量、积压数量、最老消息年龄。它们从不同角度描述积压；单看队列长度可能看不出业务等待时间。
- **Schema evolution**：消息结构随版本变化时维持生产者与消费者兼容。
- **Outbox pattern**：先在本地事务中写业务数据与待发布记录，再异步转发；解决的是数据库状态与“待发送事实”的原子记录问题，不自动保证消费者副作用一次。

### 4. 工作流：专业人员怎样设计与运行

1. **定义业务不变量和失败边界**：什么绝不能重复，什么允许延迟，消息保存多久，故障后最终状态是什么。
2. **画端到端状态转换**：从业务事务、发布、Broker 接收、投递、消费到副作用和确认，标出每一步崩溃后的状态。
3. **选择语义与拓扑**：队列还是主题、是否分区、顺序范围、保留时间、生产确认、消费确认和重试策略；这些由业务要求约束，而非产品名决定。
4. **设计消息契约**：定义事件含义、schema、稳定标识、版本规则、敏感字段与所有者。
5. **实现生产与消费**：发布失败要可判定或可对账；消费端把业务提交、幂等记录和 ack 顺序写清楚。
6. **设计失败路径**：分类可重试/不可重试错误，设置有界退避、DLQ、人工处置和安全重放。
7. **建立可观测性和容量基线**：看发布/消费速率、积压、最老消息年龄、处理延迟、失败率、重试率、DLQ、新旧 schema 错误和下游饱和度。
8. **故障注入与恢复演练**：在发布确认丢失、消费者提交后崩溃、下游超时、毒消息和 Broker 不可用时验证不变量；失败就回到对应状态边界修改。

### 5. 常见产物：可以被检查的成果

- **语义与不变量说明**：例如“同一订单可重投，但库存扣减至多生效一次”；它驱动幂等和验收。
- **消息契约 / schema**：字段、类型、语义、版本、兼容规则、示例与负责人；供生产和消费双方评审。
- **消息流与故障矩阵**：每个阶段的成功、超时、崩溃结果以及检测/恢复办法。
- **配置清单或 ADR**：记录保留、确认、重试、DLQ、分区与取舍，避免配置值脱离业务依据。
- **幂等与对账设计**：去重键、存储位置、原子边界、保留周期、冲突和补偿办法。
- **Dashboard、告警与 runbook**：展示症状，并告诉值班人员如何判断、止损、重放或升级。
- **故障测试报告**：输入条件、故障时点、观察结果、未满足的不变量和返工项。

### 6. 评价指标与判断标准：怎样知道“稳定”

- **业务正确性**：按业务主键对账“应发生、实际发生、重复发生”的数量；Broker 的发送成功率不能代替业务结果。
- **端到端延迟**：从业务事件产生到副作用完成的分位数，而非只量 Broker 内部延迟。
- **积压健康**：结合 queue depth/lag、最老消息年龄、生产与消费速率判断是否正在恶化。
- **失败与恢复**：处理失败率、重试次数分布、DLQ 新增量、恢复时间、重放成功与重复副作用数。
- **容量余量**：在峰值与下游降速时，多久会超过等待目标或保留期；扩容后是否受分区、下游连接池等新瓶颈限制。
- **可诊断性**：能否用 message ID、业务 ID、trace/correlation ID 串起生产、Broker、消费与副作用。OpenTelemetry 提供消息系统的通用属性和客户端消费计数语义，但其中部分消息指标仍标为 Development，采用时需固定版本并补产品指标。[OpenTelemetry messaging metrics](https://opentelemetry.io/docs/specs/semconv/messaging/messaging-metrics/)
- **安全与合规**：最小权限、传输/静态加密、敏感数据、保留与删除要求也属于稳定运行边界。

所有数值目标都应来自业务时限、平台限制、容量基线或明确建议，不能凭“专业感”编一个 99.99%。

### 7. 常见失败模式：从症状到验证

- **业务记录缺失**：候选原因包括生产事务与发布之间崩溃、消息过期、错误路由、提前 ack 或消费者静默失败。用业务对账逐段核对，不能看到队列为空就断言消息丢在 Broker。
- **重复扣款/重复邮件**：可能是发布超时后重发、消费成功但 ack 丢失、可见性超时过短或人工重放。按业务幂等键追踪每次投递与副作用，确认重复发生在哪一层。
- **积压持续增长**：可能是流量上涨、消费者变慢、毒消息重试、分区倾斜或下游限流。比较生产/消费速率、最老年龄、分区和错误类别后再扩容。
- **重试风暴**：无界立即重试会给故障下游叠加压力；应验证错误是否瞬时、退避是否有上限和 jitter、是否需要熔断或隔离。Stripe 的真实 API 设计说明展示了网络结果不确定时用幂等键安全重试，并用指数退避与 jitter 避免同步冲击；这是一个专业实践案例，不是 Broker 本身的保证。[Stripe：Idempotency](https://stripe.com/blog/idempotency)
- **DLQ 越来越大但无人处理**：这不是“已经可靠”，而是故障被移走。检查告警、所有者、诊断上下文、修复和重放审批是否存在。
- **顺序偶发颠倒**：检查是否误把分区内顺序当全局顺序，或重试/并行是否跨过同键消息；不要仅用时间戳排序掩盖业务因果。
- **升级后旧消费者失败**：消息 schema 破坏兼容或语义悄然改变；通过契约测试、双版本样例和消费者兼容矩阵验证。

本次检索没有找到一份可直接引用、材料完整且与“消息丢失/重复”高度对应的公开事故复盘。因此地图未把任何通用故障机制冒充真实事故结论；失败模式主要由协议行为、产品文档和真实工程实践交叉约束。

### 8. 标准与框架：哪些是规范，哪些是产品机制

- **AMQP 1.0**：OASIS 标准，规范消息格式、传输、settlement、事务和安全等互操作语义；它不是 RabbitMQ 某一版本的全部行为，也不替代应用业务一致性设计。[OASIS AMQP 1.0](https://www.oasis-open.org/standard/amqp/)
- **产品官方语义**：Kafka、RabbitMQ、SQS 等各自定义确认、保留、重试和事务的具体范围。产品间同名术语不可直接等价。
- **OpenTelemetry Messaging Semantic Conventions**：提供跨系统的 trace/metric 属性命名，帮助关联消息操作；它是遥测语义约定，不是可靠性保证。
- **SLO / error budget、故障矩阵和 ADR**：是团队组织可靠性决策的方法；没有统一的行业数值，必须绑定业务影响与证据。

## 二、贯穿案例：把“消息别丢、运行稳定一点”翻成任务

下面是完整的**教学模拟**，不是对真实系统的检查。

**教学条件**：一个订单服务在本地数据库提交订单后，向队列发送 `OrderCreated`；库存消费者扣减库存。业务允许同一消息重复投递，但同一订单的库存只能扣一次。峰值为示例性的每秒 200 个订单；业务希望已提交订单在 5 分钟内进入库存结果。技术产品尚未指定，因此案例先描述语义与验收，不替用户选 Kafka、RabbitMQ 或 SQS。

### 1. 模糊意图与待观察问题

> 消息别丢，运行稳定一点。

需要先拆成可观察问题：订单提交和发布之间是否有空窗；生产者超时后怎样重试；消费者何时写库存、何时 ack；重复投递是否重复扣库存；永久失败消息去哪里；积压怎样被发现；重放是否安全。

### 2. 教学模拟观察与诊断产物

假设对现有流程做代码走查和故障测试，得到以下**模拟观察**：

| 故障点 | 模拟观察事实 | 判断 | 要形成的修改 |
|---|---|---|---|
| DB 提交后、发布前进程崩溃 | 数据库有订单，Broker 无对应消息 | 发布与业务事务之间存在丢事件窗口 | 在同一数据库事务写入订单与 outbox 记录；转发器可重复发布 |
| 库存写成功后、ack 前崩溃 | 消息重投，库存再次扣减 | at-least-once 与非幂等副作用组合导致重复 | 以 `order_id + operation` 为幂等键，让去重记录与库存更新处于同一数据库事务 |
| 下游数据库超时 | 消费者立即重试，连接数迅速升高 | 重试放大故障 | 对明确瞬时错误做有界退避+jitter；超过次数进入隔离区并告警 |
| 一条 schema 非法消息 | 同一消息持续失败并占用处理能力 | 永久错误被当成瞬时错误 | 不立即循环重试；记录错误类型、版本和消息 ID 后进入 DLQ |
| 消费者停止 3 分钟 | queue depth 告警未触发，但最老消息年龄超过业务目标 | 只看数量不足以表达等待时间 | 同时监控最老年龄、生产/消费速率与端到端完成时间 |

这张故障矩阵就是案例中的第一个实际产物。它没有把 outbox 或 DLQ 当成固定答案：修改只针对模拟证据已经暴露的窗口。

第二个产物片段是状态约束：

> 对每个已提交订单，必须能在 `orders` 或 `outbox` 中找到待处理事实；库存事务使用 `(order_id, "reserve-stock")` 唯一键，只有首次插入幂等记录时才扣库存；ack 只能发生在库存事务提交后。重复投递允许出现，但不得产生第二次库存副作用。

### 3. 模拟验收、失败与返工

Agent 形成第一版实现后，进行模拟故障测试：

- 在业务提交后杀死生产进程并重启转发器：所有 outbox 记录最终发布，业务对账无缺口；
- 在库存事务提交后、ack 前杀死消费者：消息发生重投，但同一订单库存只扣一次；
- 注入非法 schema：消息进入 DLQ，主队列继续处理；
- 让下游数据库失败 2 分钟：重试采用退避，没有立即形成请求尖峰；
- **失败项**：恢复下游后，一次性启动大量消费者并重放 DLQ，数据库连接耗尽，正常新订单也超过 5 分钟目标。

失败说明“数据不丢”和“恢复稳定”仍冲突。返工回到恢复/容量设计：把正常流量与重放流量分开限速，设置重放批次与暂停开关，并要求重放前验证修复和幂等范围。第二轮模拟中，正常订单维持时限，DLQ 以受控速率下降；若无法同时满足，则应暴露取舍而不是偷偷扩大数据库容量。

返工链是：**恢复测试失败 → 观察到连接池饱和且新消息延迟 → 定位为无控制重放，不是 Broker 丢消息 → 增加隔离限速和操作流程 → 重测业务时限与重复副作用。**

### 4. 可复制给 Agent 的准确要求

> 请为“订单提交后异步扣库存”设计并实现可靠消息处理。业务不变量是：每个已提交订单都必须有可追踪的待处理事实；同一消息允许重复投递，但同一订单的库存预留至多生效一次。示例峰值为 200 条/秒，已提交订单应在 5 分钟内进入库存结果；这两个数值是本任务的教学条件，不要泛化成默认标准。
>
> 先画出从订单数据库事务、消息发布、Broker 接收、消费者处理、库存事务到 ack 的状态与崩溃点，并提交故障矩阵。重点验证：业务提交后发布前崩溃、发布结果未知后的重试、库存提交后 ack 前崩溃、下游超时、永久非法消息、消费者停机和人工重放。把观察事实、候选原因与选定机制分开，不要仅以“开启持久化”或“使用 exactly-once”作为端到端结论。
>
> 针对本案例已确认的窗口：订单与 outbox 记录在同一数据库事务提交，由转发器可重复发布；消费者以 `(order_id, "reserve-stock")` 为幂等键，并让幂等记录与库存更新处于同一数据库事务；仅在事务提交后 ack。瞬时错误采用有界退避和 jitter，永久无效消息进入 DLQ。DLQ 必须有告警、诊断字段、负责人、受控重放批次、限速和暂停开关，不得与正常流量无隔离地全量回灌。
>
> 交付：①状态图与故障矩阵；②消息 schema、版本与稳定标识说明；③实现及迁移/回退说明；④包含上述故障点的自动化或可复现测试；⑤dashboard、告警与 runbook；⑥按订单主键进行“应处理/已处理/重复副作用”对账的报告。验收时证明模拟崩溃后无订单事实缺口、重复投递不重复扣库存、非法消息不会阻塞主流量、下游故障时重试不形成无界风暴、恢复和 DLQ 重放时正常订单仍满足 5 分钟目标。
>
> 当前未知：具体 Broker、部署拓扑、数据库能力、可接受数据保留期、跨地域目标和真实容量基线。它们会影响确认、事务、分区、保留、灾备和数值配置；先列为决策项，不要擅自选产品或编造参数。

原来的“别丢、稳定”现在增加了：**业务不变量、端到端边界、允许重复但限制副作用、明确故障点、恢复约束、交付物和验收证据**。

## 三、学习导航与资料边界

建议按这条顺序学：

1. **先学确认时机、at-least-once 与幂等**：这是理解“为什么不丢常会带来重复”的共同基础。
2. **再学事务边界与 outbox**：能看清数据库和发布之间的空窗，而不是只盯 Broker。
3. **再学重试、DLQ、背压与恢复**：从正常路径进入稳定运行。
4. **最后按兴趣分支**：Kafka 的日志/分区/重放，RabbitMQ/AMQP 的路由与确认，SQS 的可见性模型，或流处理的状态与时间语义。

本次资料带来了三项重要修正或补充：AMQP 规范说明投递保证与 settlement 时机直接相关；Kafka 文档收窄了 exactly-once 的适用边界，尤其是外部副作用；SQS 文档说明 visibility timeout 不能消除重复。Stripe 的真实工程实践补充了结果未知时的幂等重试与退避，但它不是消息 Broker 事故复盘。公开、直接相关且材料完整的事故复盘仍是证据缺口，后续若进入具体产品，应补查该产品真实事故与版本行为。

下一步最有价值的行动是选一个副作用明确的小场景（扣库存、发邮件或生成账单），亲自画“业务提交—发布—消费—副作用—确认”五个时点，并逐点问“此刻崩溃会怎样”。你也可以继续选择“展开幂等与 exactly-once”“用 Kafka/RabbitMQ/SQS 对照同一案例”或“把我的真实需求改写给 Agent”。
