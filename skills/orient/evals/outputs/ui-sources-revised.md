# UI 设计领域地图：把“好看、专业”说准确

你真正要练的是：把感觉拆成**对象、问题维度、使用条件、限制和验收证据**。本次范围是网页与 App 的产品界面，覆盖信息组织、视觉表达、交互状态、响应式和可访问性；品牌战略、用户研究、插画、复杂动效与工程实现只标边界，不在首轮深挖。

先记住这条关系：

> 用户任务约束信息结构；结构决定内容怎样分组；交互决定怎样操作与反馈；视觉层级表达主次；组件规则保持一致；测试与标准检查结果是否真的可用。

因此，“好看”是可能出现的综合感受，不是可直接执行的改动。

## 一、八类地图

### 1. 核心实体：你在设计什么

- **用户、场景、任务**：谁在什么情况下完成什么事。任务优先级应约束界面的视觉优先级。
- **页面/屏幕**：承载一个阶段任务的整体，不是孤立海报。
- **内容与信息**：标题、说明、数据、图片、提示；真实内容长度会改变布局。
- **区域**：导航区、表单区、内容区、操作区，用来表达分组。
- **组件**：按钮、输入框、卡片、弹窗等可复用单元。真实设计系统会同时给组件、用法和代码示例；GOV.UK Design System 就按这种方式组织组件。[GOV.UK Components](https://design-system.service.gov.uk/components/)
- **状态**：默认、悬停、聚焦、禁用、加载、成功、错误、空数据。
- **视口与输入方式**：屏幕宽度、方向，以及鼠标、触摸、键盘等条件；它们约束布局和操作。

### 2. 核心概念：用什么作判断

- **信息架构（information architecture）**：内容如何分类、命名和导航。结构混乱时，换颜色通常解决不了问题。
- **视觉层级（visual hierarchy）**：位置、大小、字重、颜色、对比和留白共同表达先后与主次；它应服务任务优先级，而不是制造更多焦点。
- **分组/邻近（grouping/proximity）**：距离、容器和分隔帮助人判断哪些内容属于一组。
- **对齐/栅格（alignment/grid）**：给元素建立共同基准，使关系稳定、可预测。
- **排版层级（typographic hierarchy）**：给标题、正文、辅助信息不同但一致的角色。
- **一致性（consistency）**：相同含义采用相同表现和行为；组件与设计令牌是实现手段。
- **可供性与提示（affordance/signifier）**：让人看得出哪里能点、输入、拖动或展开。
- **反馈（feedback）**：操作后说明正在处理、已经成功或为何失败。
- **响应式（responsive）**：根据视口、内容和文字尺寸重排，不是把桌面稿等比例缩小。
- **可访问性（accessibility）**：让不同感知、运动、认知能力和输入方式的人能够获取信息并完成操作。WCAG 2.2 将颜色使用、文本对比、重排、键盘、焦点和目标尺寸等拆成可检查的成功准则。[W3C WCAG 2.2](https://www.w3.org/TR/wcag/)

### 3. 常见实用术语：用来检索和沟通

- **CTA**：期望用户执行的关键动作。
- **Primary/secondary action**：主操作/次操作，是任务优先级，不只是两种按钮颜色。
- **Whitespace**：留白，用于分组、节奏和聚焦。
- **Visual weight**：视觉重量；大小、颜色、对比和位置共同决定元素多抢眼。
- **Breakpoint**：布局发生结构变化的宽度条件。
- **Design token**：被命名并复用的颜色、字号、间距、圆角等基础值。
- **Design system**：组件、令牌、规则和文档的集合，不只是 UI 素材库。
- **Wireframe / mockup / prototype**：通常分别指结构线框、完整视觉稿和可演示交互的原型；团队用法可能不同。
- **Empty/loading/error state**：空、加载、错误状态；只画默认状态通常不足以交付。
- **Heuristic evaluation**：依据通用原则找潜在可用性问题，不能替代真实用户测试。

这组分支也得到一份公开课程路径的交叉确认：Interaction Design Foundation 的 UI Designer 入门路径同时包含视觉设计模式、Gestalt/视觉知觉和动态网站可用性，支持把“视觉表达”和“可用性”都放入地图，而不是把 UI 缩成配色与装饰。[IxDF UI learning paths](https://public-media.interaction-design.org/pdf/IDF-Course-Learning-Paths.pdf)

### 4. 工作流：怎样推进

1. 明确使用者、任务和限制，产出页面目标与内容清单。
2. 组织信息和操作路径，产出流程或页面结构；若主任务不清，回到上一步。
3. 用线框图检查顺序、分组与操作。
4. 用排版、间距、颜色角色建立视觉层级。
5. 整理组件并补齐交互、数据和错误状态。
6. 定义窄屏、长文案、文字放大和不同输入方式下的规则。
7. 用任务测试、启发式检查和可访问性标准验收；失败后返回对应环节，而非笼统“再润色”。

### 5. 常见产物：可以要求 Agent 交付什么

- 页面目标与内容清单：确认必要内容及优先级。
- 用户流程图：检查步骤与分支。
- 线框图：检查结构与操作。
- 高保真视觉稿：检查视觉表达。
- 交互原型：检查状态转换与反馈。
- 组件清单、状态表、设计令牌：保证复用与一致。
- 响应式规则：说明不同条件下怎样重排、折叠或滚动。
- 验收清单：连接设计意图与实现检查。

### 6. 评价：怎么知道结果好不好

- **任务清晰度**：未参与设计的人能否说出页面用途与下一步？
- **层级**：灰度或快速扫视时，前三个焦点是否符合任务优先级？
- **分组与一致性**：相关内容是否成组；同类组件是否同义同形？
- **可读性**：长标题、真实数据和文字放大后是否仍成立？
- **反馈与恢复**：加载、成功、失败是否可见；出错后能否修改而不重输？GOV.UK 的真实错误组件指南要求字段旁给具体错误信息，并保留用户已填内容。[GOV.UK Error message](https://design-system.service.gov.uk/components/error-message/)
- **适配性**：窄屏、宽屏和键盘下能否完成核心任务？
- **可访问性**：焦点是否可见、信息是否不只依赖颜色、相关对比与目标尺寸是否按选定 WCAG 等级实测？

### 7. 常见失败模式：症状不是诊断

| 症状 | 候选原因 | 验证方法 |
|---|---|---|
| 所有东西都抢眼 | 任务优先级不清，或颜色、尺寸、字重同时滥用 | 先列主次任务，再看焦点是否匹配 |
| 页面拥挤 | 内容过多、分组不清、密度高或容器窄 | 分别改变内容、分组和宽度，不能直接归因于“留白少” |
| 简洁但不会用 | 控件隐藏、标签含糊或反馈缺失 | 让未见过页面的人完成一个任务并观察卡点 |
| 视觉稿漂亮，实现后崩坏 | 只用了短文案、单尺寸和默认状态 | 注入长文案、错误、小屏和放大文字 |
| 错误后反复重填 | 错误信息不具体或清空了输入 | 制造验证错误，观察能否定位、理解并修复 |
| 键盘用户迷失 | 焦点不可见、顺序异常或被遮挡 | 全程只用键盘检查；焦点状态的用途和实现可参照 GOV.UK 的真实设计系统产物。[GOV.UK Focus states](https://design-system.service.gov.uk/get-started/focus-states/)

相邻场景的真实研究补充了两条边界。Baymard 在电商结账测试中观察到：经历过表单错误的参与者会为避免再次报错而填写本不确定是否需要的信息；这支持“错误设计会改变后续行为”，但不能直接推出 SaaS 注册页的转化率。[Baymard：Avoid Repeat Form Errors](https://baymard.com/blog/avoiding-repeat-form-errors) 另一项结账表单研究记录了消失标签导致纠错困难，也展示了过严邮箱校验会阻挡含 `+` 的地址；因此地图增加了“标签可持续辨认”和“校验规则可能制造假阴性”，而不是把所有校验都当成越严格越专业。[Baymard：Form Design](https://baymard.com/blog/form-design)

### 8. 标准与框架：强制性不同

- **WCAG 2.2**：W3C Web 可访问性标准；采用时要明确适用范围与目标等级。
- **平台指南**：如 Apple HIG，适合查对应平台的布局、组件和行为习惯，不是所有网页的强制标准。
- **设计系统**：某组织在自身场景采用的组件和规则。GOV.UK 的做法证明“该系统这样取舍”，不能自动升级为所有产品最佳实践。
- **启发式与 checklist**：用于发现遗漏风险，不等同于合规结论或用户研究结果。GOV.UK Service Manual 的表单结构建议以“一页一件事”作为政府服务的起点，同时明确是否合并页面应由用户研究判断；这说明 checklist 必须保留场景条件，不能机械套用到高频内部工具。[GOV.UK：Structuring forms](https://www.gov.uk/service-manual/design/form-structure)

## 二、贯穿案例：把“注册页专业一点”变成要求

以下是**教学模拟**，不是真实页面实测。假设对象为桌面与手机共用的 SaaS 注册页；流程固定为“邮箱 + 密码 → 创建账户”，允许调整布局、文案和视觉；案例把邮箱注册定为主路径、Google 注册为次路径。品牌风格、设计系统和合规等级未知。

模拟观察：现稿标题只有“欢迎”；大插画隔开标题与表单；两个注册按钮同样醒目；输入标签在输入后消失；错误只显示红框；固定宽度表单在 360px 下截断；键盘焦点不可见。

这些观察支持“用途不清、主次不明、错误反馈依赖颜色、窄屏与焦点状态缺失”，不支持“字体不高级”之类判断。于是形成产物片段：

```text
创建账户
用邮箱开始使用 Acme

邮箱
[ name@example.com           ]
密码                    [显示]
[ ••••••••                   ]
[错误] 输入产品实际规则要求的密码

[      创建账户      ]  主操作
--------- 或 ---------
[   使用 Google 注册  ]  次操作
已有账户？登录
```

状态表同时规定：聚焦时有可见轮廓；错误时保留输入并显示具体原因和恢复方式；提交中说明状态并防止重复提交；窄屏容器收缩并保留页面边距。

模拟验收：360px 下不再截断，暂时通过；错误文字可读且输入保留，暂时通过；“显示密码”的焦点仍不明显，返回组件状态修正；灰度下两种注册方式仍近似同权重，返回视觉层级继续降低次操作。没有真实对比测量、屏幕阅读器检查或用户测试，所以不能宣称合规或注册效果提高。

可复制给 Agent 的自足说明：

> 这是教学模拟任务，不是对真实页面的诊断。对象是桌面与手机共用的 SaaS 注册页；流程固定为“邮箱 + 密码 → 创建账户”，允许调整布局、文案与视觉，但不增删字段或改变流程；邮箱注册是主路径，Google 注册是次路径。请先审查实际页面。下面的“标题含糊、插画打断阅读、两个注册按钮同权重、标签消失、错误只用红框、窄屏截断、焦点不可见”均为模拟观察，必须逐项复核后才能据此修改。
>
> 目标是让首次访问者理解页面用途、识别邮箱注册主操作、完成注册并从错误中恢复。若实际证据支持，调整信息层级、分组、持久标签、主次操作、错误反馈、键盘焦点和窄屏重排；不要仅增加阴影、渐变或装饰。密码错误文案必须使用产品真实规则；若规则未提供，标为待确认，不虚构字符数。
>
> 交付诊断记录、桌面与手机线框、视觉方案、组件状态表和验收清单。360px 是本教学任务指定的示例验收视口，并非行业通用值；验收还覆盖键盘全流程、真实长错误文案和文字放大。可访问性按项目最终选定的 WCAG 2.2 等级实测。仍未知：更具体的目标用户特征、品牌风格、现有设计系统、完整设备/浏览器范围、密码规则和合规等级；这些会影响最终方案。允许改动的范围和流程已经在首段确定，不再列为未知。

这里新增的不是“高级感”同义词，而是对象、目标、待验证现象、允许范围、产物、边界条件与验收证据。

## 三、后续导航

推荐顺序：先学任务、信息架构和视觉层级，因为它们决定什么重要；再学分组、对齐、排版、间距与颜色角色；随后学组件、状态和设计系统；最后用响应式、可用性和可访问性把要求闭环。品牌、动效和研究方法可按目标选读。

本轮资料实际改变了地图：WCAG 把“可访问”拆成不同等级的成功准则，因此不能笼统声称合规；GOV.UK 的组件产物把错误信息、保留输入和焦点状态落到交付细节；其 Service Manual 又提醒结构建议要随任务频率和用户研究调整。Baymard 的相邻表单研究补入了“错误会影响后续填写行为”“消失标签妨碍纠错”“过严校验可能阻挡合法输入”三种失败机制。它们可迁移为 SaaS 注册页的检查问题，不能直接迁移电商样本的发生率或效果数字。教学案例仍是模拟，实际诊断和效果需要真实页面与测试。

下一步最有价值的是选一张真实界面截图，做一次“观察现象 → 区分候选原因 → 写成条件化要求 → 定义验收”。你也可以让我展开“视觉层级”，或让我把你下一句模糊需求改写给 Agent。
