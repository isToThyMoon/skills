# 知识获取流程复测

## 范围与结论

本轮新增 references/sources.md，将模型内化知识明确为候选结构和解释基础，外部资料用于补全、核实和挑战，而非每句都必须引用。保留八类地图、五层理解、不记录学习进度的设计。

UI 与消息队列测试复用 GPT-5.6 Sol 会话；离线测试复用另一个评审会话。不是新上下文盲测，也没有对真实用户学习收益或最终 Agent 成品做对照实验。评估为主 agent 阅读原文与关键来源抽查，不是执行 agent 自评分。

结论：有实质改进，尚不能认定首次调用稳定覆盖所有来源类型。UI 经反馈达到本轮来源目标；消息队列仍只有部分通过；离线来源边界通过。最终强化的逐项引用检查规则未再做全新首轮测试。

## 来源实际影响，而非链接数量

UI 增加了错误之后的填写行为、持久标签、校验假阴性等失败机制，并把相邻电商研究限定为检查问题，未套用转化率。GOV.UK 的表单指导用于限制“一页一件事”的泛化。相关证据对应见 [UI 来源记录](outputs/ui-sources-final-evidence.md)。

消息队列将 Broker 成功与业务成功分开，并指出外部系统副作用不因使用 exactly-once 术语就自动保证一次。其 [来源记录](outputs/messaging-sources-evidence.md) 以产品与协议文档为主，Stripe 是实际工程设计但不是 Broker 事故复盘；诚实披露缺口不等于已经完成该类调研。Kafka 引用为 4.0 文档，回答应更明确写出版本范围。

## 抽查与残余问题

主 agent 实际打开 GOV.UK 错误组件、焦点与表单结构页面、Baymard 表单/重复错误/校验专项文章和 Kafka 设计文档。核对了关键主张与链接，不代表逐句事实审计。

UI 原来把含 + 邮箱被拒案例挂到通用表单文章。针对性核查后改引 [Baymard 专项文章](https://baymard.com/blog/validations-vs-warnings)，原始版本保留，不覆盖失败证据。这推动 sources.md 强化“具体例子逐项核对，主题相关不等于支持细节”。

消息队列模拟中“停机 3 分钟却已超过 5 分钟目标”缺少原有积压或时间起点，不能直接推出；其状态不变量也可进一步收紧，避免 orders 中有记录便被误认为 outbox 完整。该回答保留为部分通过样本，没有包装成可直接生产实施的方案。

离线小说案例有文本片段和验收办法，但没有真正走完模拟验收失败后的修订；离线诚实性通过不代表其他所有交付项通过。

## 本轮修正与验证边界

- 将候选地图、互补获取、主张级交叉检查和来源影响说明设为默认流程；小型需求翻译不强制完整调研。
- 根据 UI 首轮失败明确：真实失败来源不必与教学案例完全同场景，须说明迁移边界。
- 根据引用抽查明确：具体案例不能误挂到主题相近的引用下。
- 未添加学习档案、强制考试或固定引用数量；未承诺一小时掌握。

下一轮最值得验证的是新上下文下能否主动找到真实失败资料，并在无人提醒时准确对应具体主张。本轮只能证明流程能产生有用补充并暴露错误，不能证明高可靠性已普遍成立。
