# 八类领域地图的交付方式

## 首轮交付结构

依次给出四部分：领域总览 → 八类地图 → 一个贯穿案例 → 后续导航。先建立全景，再用具体案例展示如何使用；用户无需先提供项目。深度随用户需求调整，首轮四部分均有实质内容，不将案例推迟到“下次可以做”。

## 1. 领域总览

先用一小段说明领域解决什么问题、主要子域及本次边界。随后给一个骨架关系图或简明关系描述，让初学者先知道不同部分为何在同一张图中。必要的专业词在首次出现时用普通话解释。

## 2. 八类地图

| 类别 | 回答的问题 | 条目需要说明的内容 |
|---|---|---|
| 核心实体 Entities | 这个领域研究、操作或管理什么？ | 对象是什么、承担什么角色、与谁发生什么关系 |
| 核心概念 Concepts | 靠哪些原理或区分理解问题？ | 解决/解释什么问题、与哪些概念有何关系、关键边界 |
| 高频专业术语 Vocabulary | 专业人士如何命名和检索这些东西？ | 中文含义、常用原文/别名、实际使用语境、指向对应概念 |
| 工作流 Workflow | 专业工作通常怎样推进？ | 阶段目标、输入输出、决策点、反馈和返工，不假定总是线性 |
| 常见产物 Artifacts | 工作留下哪些可检查的成果？ | 谁制作/使用、用于什么决策、包含什么、连接哪个阶段 |
| 评价指标与判断标准 Evaluation | 怎么判断好坏？ | 测量或观察方法、适用条件、与其他目标的取舍 |
| 常见失败模式 Failure modes | 常见的出错方式和征兆是什么？ | 可见症状、候选原因、影响、验证方法、相关环节 |
| 标准与框架 Standards / frameworks | 哪些规则或方法组织工作？ | 发布方、用途、范围、强制标准/推荐指南/方法框架的区别 |

这八类是观察角度，不是互斥分类。例如“设计 token”可以是概念、术语和产物；选一处解释完整，其余交叉指向。高频术语区作为检索索引，不能把其余七区复制一遍。没有语料时把高频理解为“常见实用术语”，不伪造频次排名。

若领域没有正式标准，明确说明并列实际存在的指南或方法；不得为填满类别编造标准。

自行归纳的记忆口诀或分析顺序标为“本回答的组织方式”，与可追溯的行业框架分开；不能给它起英文名后就当作业内通用框架。

选择条目时先覆盖主要子域，再选能解释关键决策或支撑检索的概念；同义词合并。按领域复杂度和用户要求控制篇幅，剩余分支明确列入未展开范围。全景指主要结构可见，不表示穷尽所有条目。

每个核心条目交代名称、用途和明确关系；纯索引词可指向已解释的条目。关系可在同类或跨类之间，用“约束、依赖、测量、可能导致、替代”等动词表达。围绕重要问题解释关系成立的理由和适用条件，使读者知道何时需要一起考虑这些概念，而不只看到名词相邻。

例如：“任务优先级约束视觉层级；排版、对比和位置共同表达这种层级。若多个操作都抢眼，先检查操作优先级是否明确，再判断是否需要调整样式。”这是关系的讲法示例，不是所有领域都套用的内容。相关概念可以合并解释，不给每个词机械附加整套模板或 prompt，也不以开头的总关系图替代条目之间的解释。

## 3. 一个贯穿案例

选一个具体对象与有限目标，如一个设置页、一次访谈录制；泛指“一个页面”或罗列行业步骤不足以构成案例。无真实材料时标明“教学假设”，列出案例条件；假设的观察结果也标明，不冒充实际调查。案例只是领域的一种路径，不把其取舍提升为普遍要求。

用同一个案例实际走过：目标与实体 → 检查材料/证据 → 用相关概念作选择 → 形成具体产物 → 用评价方法检查 → 失败时返回对应环节。给出一组真实观察或明确标注的模拟观察，据此展示具体选择、一个产物片段及验收后的处理。例如可以展示调整后的结构草图、诊断清单条目或方案片段，不必制作完整成品。教学中模拟的验收结果同样标明；不能仅罗列未来应做的检查和条件分支，再以“请 Agent 生成产物”结束案例。

在案例中展示约束的来历，而非只附一段长 prompt：

| 转化环节 | 要交代的内容 |
|---|---|
| 模糊意图 | 原始表达与希望改善的结果 |
| 待观察问题 | 哪些现象需要检查，可能有哪几种解释 |
| 证据与条件 | 已知事实、明确的教学假设、仍未知的条件分别是什么 |
| 领域判断 | 哪些概念帮助区分解释，什么结果会支持哪项选择 |
| 可执行要求与验收 | 应检查或修改什么，如何确认改善且未破坏其他要求 |

缺少观察证据时交付检查要求或条件化修改要求；证据支持后才能写确定修改。最终需求只使用已知条件或明确标注的示例假设；不能前文确定受众、平台、数量或目标值，后文又将同一项列为未知。涉及经验建议时说明条件与取舍，避免把建议写成无条件规则。

## 4. 后续导航

推荐阅读路径给出“为什么先看它”，区分理解所需的先决概念和按兴趣选读的分支。给少量权威入口并说明各自适合查什么；关键具体主张在附近附来源，不用末尾书单代替证据。

在导航中按 [知识获取规则](sources.md) 简述资料对地图的补充/修正及证据缺口；来源与主张对应，避免只有末尾书单。

最后指出本次尚未覆盖的方向、当前不确定的地方。用户未指定后续且未表示结束时，在完整交付后简短邀请，例如：“下一步建议从这张地图中挑出最值得优先理解的核心概念，按理解依赖排列，并说明它们能帮助你向 Agent 提出什么要求。要继续吗？也可以指定一个分支深入。”邀请不阻挡初版交付，不要求用户先选数量、找项目或做练习。

若用户已要求地图和学习顺序，在本轮直接按 [learning.md](learning.md) 完成筛选与排序，不重复询问；已有明确后续任务则直接衔接该任务。

## 交付前检查实际内容

- 八类是否有实质项或不适用理由，主要子域是否覆盖或明确列入边界？
- 核心概念是否有用途、关系及重要关系的理由，而非只有释义？
- 同一具体案例是否走过决策、产物、评价和返工，而非只有通用流程或长 prompt？
- 每项约束是否可追溯到已知条件、观察证据或明确的教学假设，且与未知项一致？
- 是否把候选原因写成诊断，或把有条件的建议写成普遍规则？
- 资料是否实际补充、确认或修正了地图，真实产物和失败案例是否有内容落点或明确的获取缺口？

发现缺口时修订对应内容。自检是输出检查，不能据此宣称用户已理解或方法已获成效验证。
