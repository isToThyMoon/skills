# 测试审计

项目有测试时读。目标：测试只留下值得它的构建和等待时间的那部分，日常检查快到 agent 愿意频繁运行。

LLM 写的项目常见测试比功能代码还多，还有很多防不到真实错误。有 AI coding 时，多数问题发现后很快能修好，所以一个测试要能回答：**它防的是哪种真实可能发生的错误？这种错误出现后，等发现了再修为什么来不及？** 答不上来就删。

## 判定标准

**留下**，至少满足一条：

1. 出错后果难挽回：资金和计费、数据丢失或迁移、鉴权和权限、安全。
2. 守外部契约：对接的协议、序列化格式、公开 API，这些出错时本地编译发现不了。
3. 复杂的纯逻辑：看代码判断不出对错的算法、状态机、并发调度。
4. 同类 bug 真实发生过且反复出现。
5. 一条主流程冒烟：证明应用还能跑起来。每个应用留一条就够。

**删除**，命中任一条：

- 复述实现：断言常量、默认值、getter、枚举，或把实现再写一遍。
- 测框架和语言本身的行为。
- mock 掉了被测逻辑，只验证调用过某个方法。
- 同一行为在不同层重复测，或多组参数走同一条路径。留最有价值的一个，能用表驱动合并的就合并。
- 快照和界面结构断言，没人会真看它们的 diff。
- 长期跳过或偶发失败的。
- 只为覆盖率写的，以及只服务于已删测试的 helper 和 fixture。

拿不准时按删除处理，除非它沾上第 1 条。项目文档（ADR 等）写明要保留的测试留下，并在报告里列出，由用户决定是否修改那条规则。

## 步骤

1. **基线。** 运行 `python3 <skill 目录>/scripts/test_inventory.py <repo> --list`，把输出存进 `$TMPDIR/setup-harness/tests.md`。在改动前串行跑一次现有的完整测试，记下耗时和失败；失败的重跑一次，区分稳定失败和偶发失败。构建要超过 10 分钟时先跳过全量，只记录原因。
2. **审计。** 把测试文件按模块分组，不超过 8 组，小项目就一组。每组在全新上下文里启动一个不改仓库的子 agent（不支持子 agent 的工具就分批自己读）。prompt 里给它：上面的判定标准全文、这组的文件列表、产品一句话和第 2 步记下的出错代价最高的地方，要求它读代码、不跑构建，为每个文件写 `留 / 删 / 部分删` 和一句理由，引用命中的标准，只写 `$TMPDIR/setup-harness/tests-<组名>.md` 这一个文件。
3. **删减。** 执行审计结论，清掉随之失效的 helper 和 fixture。生产代码保持原样；只被测试用到的生产代码列进报告。审计发现第 1 条范围内的测试缺口时，这次不补，写进报告由用户决定。
4. **改流程。** 把项目里要求先写测试、TDD 或覆盖率门槛的文档和配置改掉，CI 和 pre-commit 里的测试步骤同步精简，只保留快速检查和留下的测试。lint、安全、部署等其他步骤保持原样。
5. **写门槛。** 在 `AGENTS.md` 的"测试"一节，写明这个项目值得测试守住的具体地方，让之后的 agent 默认把时间花在功能上。
6. **验证。** 只跑受影响的测试目标，修掉删除带来的编译错误。修不好的恢复对应文件，并写进报告。

## 完成条件

- `tests.md` 里每个测试文件都有结论。
- 删除的测试文件、断言或用例都能对应到一条删除标准，留下的都能对应到一条留下标准。
- 项目里不再有强制 TDD、覆盖率门槛或"改动必须加测试"的要求，除非用户明确要求保留。
- 再运行一次 `test_inventory.py`，精简前后的文件数、行数和比例都记进 `plan.md`。
- 受影响的测试目标能编译并通过，或失败已确认在铺设前就存在。
