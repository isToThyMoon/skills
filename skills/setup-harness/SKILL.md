# Setup Harness

目标是让之后每个 coding agent 在新会话里都能快速定位需求点，把时间花在功能开发上，并沿用项目的技术栈、架构和视觉风格。harness 只提供信息和反馈，具体怎么干活留给之后的 agent。

这份 skill 对你也一样：下面写清要交付什么、有哪些信息可用、怎么验收。盘点什么、先做哪块、怎么组织工作，都按项目情况自己判断。`assets/`、`references/`、`scripts/` 都相对于本 skill 所在目录，不是目标仓库。

每句要写进 harness 的话都过一道筛子：**删掉它，agent 会犯错吗？它能从代码、配置或 `ls` 查到吗？** 只留"会犯错且查不到"的。研究显示 agent 会照做文件里的指令，多余内容会让任务变难、成本变高，而目录概览并没有帮它更快找到文件（[arXiv 2602.11988](https://arxiv.org/html/2602.11988v1)）。所以目录靠 `ls`，定位靠词表和 grep。

测试也过同样的筛子。有 AI coding 时，多数问题发现后很快就能修好，测试只守修复来不及或发现不了的地方；其余测试的构建和等待都是浪费。

## 交付结果

- **入口文档**：根目录的 `AGENTS.md` 是主文件，`CLAUDE.md` 全文只有一行 `@AGENTS.md`，其他工具的规则文件把通用内容迁入后只留工具专属配置；有 `.gemini/` 或 `.aider.conf.yml` 时，按 <https://agents.md> 的说明指向 `AGENTS.md`。用项目已有文档的语言，没有文档时用与用户对话的语言。`assets/AGENTS.template.md` 可作起点。
- **词表**：需求用语和代码命名之间的桥，agent 查到词就能 grep。`assets/GLOSSARY.template.md` 可作起点。
- **默认检查**：一条改完就跑的命令，结果可信，快到 agent 愿意频繁运行，写进 `AGENTS.md`。
- **UI token**（有界面时）：读 `references/ui-tokens.md`。
- **精简后的测试**（有测试且用户同意后）：读 `references/test-audit.md`。
- **报告**：见“验收”。

空仓库还要定技术栈，并用官方脚手架起一个能启动的骨架，这样目录和配置都符合生态习惯。已有的 harness 全部按本 skill 的标准优化，文件可能是 `AGENTS.md`、`CLAUDE.md`、`GEMINI.md`、`.cursor/rules/`、`.cursorrules`、`.github/copilot-instructions.md`、词表、检查脚本或 token。

跨会话要用的结论记进 `$TMPDIR/setup-harness/plan.md`，放在仓库外，免得混进 diff，并写明仓库路径。

## 硬边界

这几条错了难挽回，或者本来就该由用户决定，其余都可以按项目情况调整：

- **开始时工作区干净。** 有未提交改动时，请用户先提交或 stash，这样产出才是一份能单独审查的 diff。不是 git 仓库时，用户同意后再 `git init`。
- **测试删减排在最后，用户同意才做。** 这是唯一固定的顺序：先交付其他结果并报告，用户看过测试规模和成本后再决定。建议先提交核心产出，让测试删减成为单独的 diff。用户只要测试审计时，可以直接做。
- **时间主要用来读仓库，写语义地图和词表，这次不查测试问题。** 这些产出只能靠读代码得来。测试只为验证默认检查才跑，通常一次就够，耗时优先取已有文档或 CI 记录，因为反复跑既占机器，也让用户干等。失败和偶发失败记下用例名写进报告，复现和查根因由用户决定。
- **用户要求时才提交。** 产出留在工作区供审查。
- **旧代码和架构保持原样。** 批量改名、加注释或迁移样式会让 diff 无法审查，也可能带来业务风险。业务代码留给之后的任务。
- **不新增 hook、pre-commit 和 CI。** 这些留给同样的错反复出现之后，再由用户决定。现有的是用户有意的强制手段，只有其中的测试步骤可以随测试审计精简；其他多余的写进报告。`CLAUDE.local.md` 是个人文件，保持原样。
- **删除和迁移都有交代。** 每条删掉或挪走的事实，都能在报告里查到去向或理由。

## 可用的信息

### 问用户什么

只问代码里读不到的，附上推荐答案，尽量一次问完。通常是产品一句话、核心业务词、架构上不能破的约束、这个项目出错代价最高的地方。

### 旧内容放哪

| 这条事实 | 去向 |
| --- | --- |
| 通用、关键、处处要用 | 根 `AGENTS.md` |
| 只对某个子项目或目录成立 | 该目录的 `AGENTS.md`，旁边配一个只写 `@AGENTS.md` 的 `CLAUDE.md`（根目录有 `CLAUDE.md` 时，Claude Code 默认不读 `AGENTS.md`，靠这个 import 才加载） |
| 只在某类任务时才用 | 该主题已有的文档，根 `AGENTS.md` 留触发条件 |
| 决定和原因 | `<repo>/docs/adr/` |
| 业务词 | 词表 |
| 只对 Claude Code 成立 | `.claude/rules/` |
| 测试要求（先写测试、TDD 等） | 改写成 `AGENTS.md` “测试”一节的门槛；配置里的覆盖率门槛和 CI 测试步骤随测试审计处理 |
| 与代码不符 | 核对代码后修正 |
| 能查到、模型默认会做、或泛泛而谈 | 删除 |

### 入口文档和词表

- **语义地图**只写 `ls` 看不出的：哪块业务在哪、哪里不再加新功能、哪里容易改错。
- **词条**给出代码里能 grep 到的真实标识，不写路径，因为标识比路径稳定。业务叫法拿不准的请用户确认。通用技术词和代码里没有对应概念的词不必收；空仓库的标识可以先写 `待定`。
- **已有词表**沿用原格式，补上标识。名为 `CONTEXT.md` 的是旧叫法，`domain-modeling` 等 skill 只认 `GLOSSARY.md`，可以建议用户 `git mv` 改名并同步引用。词条带标识和 `domain-modeling` 不写实现细节的约定不同，这是为了 grep 有意保留，在报告里说明。
- **测试门槛**用出错代价最高的地方来写，让之后的 agent 默认把时间花在功能上。其他要求先写测试的文档同步改掉；文档点名的测试不在这里改，见 `references/test-audit.md`。没有测试时不补测试。
- **命令**：验证新增和改动的；保留下来的旧命令不必为验证文档而重跑。要设备、其他系统或凭据的，写进报告。

### 检查入口

- **复用现有命令。** 优先用项目已有的命令或技术栈惯用入口（`make check`、`npm run check`、`just check`），没有时才写一个尽量薄的 `<repo>/scripts/check`。工具没有声明时，把安装命令写进 `AGENTS.md`；产物写进 `.gitignore`。
- **够快。** 要快到 agent 愿意每次改完都跑，超过几分钟时把原因写进报告。慢测试、E2E 和整包构建放到单独的目标，写明什么时候才跑；多端项目可以只跑改动的一端，本机跑不了的打印 `SKIP` 和替代命令。
- **退出码可信。** 之后的 agent 靠退出码判断，所以默认命令要能通过。历史失败和偶发失败可以排除或只查改动过的文件，并把用例名写进报告。失败信息写明怎么修。
- **设超时。** 免得挂死的测试无声地卡住流程。超时算失败，并报告卡在哪。

### 测试审计值不值

先用 `python3 <skill 目录>/scripts/test_inventory.py <repo>` 看规模。审计的主要收益是少维护、少读。删用例通常不提速，因为并行测试的总耗时由最长的那条链决定；提速主要靠把慢测试移出默认检查。向用户说清这点，不要按提速来承诺。上下文用掉很多时，可以在新会话里靠 `plan.md` 接着做。

## 验收

**默认检查。** 交付前跑一次，确认它通过，并且真的执行了检查而不是空跑。

**定位测试。** 已有代码时，找一个全新上下文的 agent（不支持子 agent 的工具，请用户在新会话里跑），只给仓库路径和只用业务词描述的需求，看它能否顺畅地找到主要要改的文件。需求不提文件名和标识符。它找错或绕了很多路时，修正词表或语义地图后再测。结果和搜索次数写进报告。

**报告。** 告诉用户：

- 分支，新建和改动的文件，改动还没提交、请用户审查 diff；
- 删减或迁移的每条事实和去向；
- 检查命令、耗时和涉及的目标，排除和偶发失败的用例，没跑的命令和原因，定位测试结果；
- 请用户确认的词条和设计决定，词表要深入打磨时可以用 domain-modeling skill；
- 项目有测试时，给出测试规模、已知耗时和审计的预计成本，问要不要审计；
- 做了测试审计时，精简前后的文件数、行数、比例和默认检查耗时，保留了哪些、为什么，以及发现的高风险测试缺口。

完成条件：默认检查通过；定位测试通过，或未通过的情况已写进报告；以上结果都有交付，或说明了为什么不适用；报告覆盖以上各项。
