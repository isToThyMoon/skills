# Setup Harness

目标是让之后每个 coding agent 在新会话里都能快速定位需求点，把时间花在功能开发上，并沿用项目的技术栈、架构和视觉风格。harness 只提供引导和反馈，大部分决定留给之后干活的 agent。`assets/`、`references/`、`scripts/` 都相对于本 skill 所在目录，不是目标仓库。

每句要写进 harness 的话都过一道筛子：**删掉它，agent 会犯错吗？它能从代码、配置或 `ls` 查到吗？** 只留"会犯错且查不到"的。研究显示 agent 会照做文件里的指令，多余内容会让任务变难、成本变高，而目录概览并没有帮它更快找到文件（[arXiv 2602.11988](https://arxiv.org/html/2602.11988v1)）。所以目录靠 `ls`，定位靠词表和 grep。

测试也过同样的筛子。有 AI coding 时，多数问题发现后很快就能修好，测试只守修复来不及或发现不了的地方；其余测试的构建和等待都是浪费。

重检查（全量测试、整包构建）整个流程最多跑两次：精简测试前的基线一次，收尾一次，其余时候只跑和当前改动相关的部分。默认的快速检查不限次数。产出留在工作区供用户审查，用户要求时才提交。

## 1. 盘点现状

运行 `git status --porcelain`。有输出时停下，请用户先提交或 stash，这样本次产出才是一份能单独审查的 diff；不是 git 仓库时，征得用户同意后 `git init`。

然后按实际情况选分支（可以同时命中"已有代码"和"已有 harness"）：

- **空仓库**：还没有业务代码。
- **已有代码**：一切从代码、配置、测试、README 和 git 历史提取，架构保持原样。
- **已有 harness**：存在 `AGENTS.md`、`CLAUDE.md`、`GEMINI.md`、`.cursor/rules/`、`.cursorrules`、`.github/copilot-instructions.md`、词表（`GLOSSARY.md`、`CONTEXT.md` 等）、检查脚本或 token 中的任何一个。全部按本 skill 的标准优化，其中 `AGENTS.md` 是主文件。

再判断项目有没有界面（Web、App、桌面端都算）。把分支、是否有界面、已有 harness 文件清单和待问用户的问题写进 `$TMPDIR/setup-harness/plan.md`（放在仓库外，免得混进 diff）。

完成条件：工作区干净，`plan.md` 写明分支和是否有界面，已有 harness 的每个文件都列在清单里。

## 2. 定下项目事实

只问代码里读不到的，每个问题附上推荐答案，一次问完：产品一句话、核心业务词、架构上不能破的约束、这个项目出错代价最高的地方。

**空仓库**还要定技术栈，再用该技术栈的官方脚手架起骨架（例如 `npm create vite`、`flutter create`），这样目录和配置都符合生态习惯。skill 本身不内置技术栈模板。业务代码留给之后的任务。

**已有 harness** 审计旧内容，在 `plan.md` 里给事实记去向。删除和迁移的逐条记，保留原位的可以合并成一行：

| 这条事实 | 去向 |
| --- | --- |
| 通用、关键、处处要用 | 留在根 `AGENTS.md` |
| 只对某个子项目或目录成立 | 该目录的 `AGENTS.md`，旁边配一个只写 `@AGENTS.md` 的 `CLAUDE.md`（根目录有 `CLAUDE.md` 时，Claude Code 默认不读 `AGENTS.md`，靠这个 import 才加载） |
| 只在某类任务时才用 | 该主题已有的文档，根 `AGENTS.md` 留触发条件 |
| 决定和原因 | `<repo>/docs/adr/` |
| 业务词 | 已有词表，沿用原文件名；没有时新建 `GLOSSARY.md` |
| 只对 Claude Code 成立 | `.claude/rules/` |
| 测试要求（TDD、覆盖率门槛等） | 第 4 步按 `references/test-audit.md` 处理 |
| 与代码不符 | 核对代码后修正 |
| 能查到、模型默认会做、或泛泛而谈 | 删除，并在报告里写明理由 |

现有的 hook、pre-commit、CI 是用户有意的强制手段，其中的测试步骤在第 4 步精简，其余保持原样；觉得多余的写进报告，由用户决定。`CLAUDE.local.md` 是个人文件，也保持原样。

完成条件：`plan.md` 的问题清单逐条有答复；空仓库的骨架能启动；已有 harness 中删除和迁移的每条事实都有去向。

## 3. 写入口文档

从 `assets/AGENTS.template.md` 和 `assets/GLOSSARY.template.md` 起稿，写出根目录的 `AGENTS.md` 和词表；用项目已有文档的语言，没有文档时用与用户对话的语言。`CLAUDE.md` 全文只有一行 `@AGENTS.md`。

- **语义地图**只写 `ls` 看不出的：哪块业务在哪、哪里不再加新功能、哪里容易改错。
- **词表**是需求用语和代码命名之间的桥，所以每个词都给出代码里的真实标识，agent 查到标识就能 grep。标识比路径稳定，词条不写路径。已有代码时从代码提取核心业务词；业务叫法拿不准的，列进报告请用户确认。已有词表（包括 `CONTEXT.md`）沿用原文件名和格式，只补标识，这样不用牵动引用它的文件。
- **面向 grep 的写法**管今后写的代码。铺设时旧代码保持原样，批量改名和加注释会让 diff 无法审查，也可能带来业务风险。
- **其他工具**：仓库有 `.gemini/` 或 `.aider.conf.yml` 时，按 <https://agents.md> 的说明把它们指向 `AGENTS.md`。其他工具的规则文件把通用内容迁入 `AGENTS.md` 后，只留工具专属配置。

文档里的命令：新增和改动的要跑一次；保留下来的旧命令不为验证文档而重跑，尤其是重构建。要设备、其他系统或凭据的，写进报告。

完成条件：新增和改动的命令都跑过或已说明原因；除了第 4、5 步才定下的测试门槛和检查命令，模板占位符都已替换或删除；词表包含产品一句话里的业务概念，通用技术词和代码里没有对应概念的词不收（空仓库的标识待首次实现时补，先写成 `待定`）。

## 4. 精简测试

项目有测试时，读 `references/test-audit.md`，按其中的步骤审计并直接删减。这一步是本 skill 的重点之一，要大刀阔斧：删除都在未提交的 diff 里，随时能恢复，需要时 AI 也能很快重写。

没有测试时不补测试。空仓库只在 `AGENTS.md` 里写好测试门槛。

完成条件：`references/test-audit.md` 末尾的完成条件都满足；没有测试时，`AGENTS.md` 的"测试"一节已写明这个项目值得测试守住的地方。

## 5. 建检查入口

提供一条默认命令，做日常改完就跑的快速检查：格式、lint、类型检查或编译，加上第 4 步留下的快速测试。目标是有缓存时 2 分钟内跑完，这样 agent 才愿意频繁运行它。技术栈有惯用入口时（`make check`、`npm run check`、`just check`）用它，没有就写 `<repo>/scripts/check`。

- 整包构建、E2E、全量测试放到单独的目标（例如 `scripts/check full`），写明什么时候才跑。
- 多端项目支持按目标只跑改动的一端。某一端在本机跑不了时，打印 `SKIP` 和替代命令，并写进报告。
- 自写检查的失败信息写明怎么修，agent 下一步会照着做。
- 不新增 hook、pre-commit 和 CI，这些留给同样的错反复出现之后，再由用户决定。
- 运行检查会留下产物时，把它们写进 `.gitignore`；工具没有声明时，把安装命令写进 `AGENTS.md`。

默认命令要能通过，之后的 agent 才能靠退出码判断。历史失败不属于本次范围，修它们可能牵动业务，所以这样处理并写进报告：格式和 lint 只查改动过的文件，整仓格式化由用户决定是否单独提交一次；失败的测试从默认命令里排除，并写明排除了哪些。

完成条件：默认命令退出 0 并写进 `AGENTS.md`，排除的每一项都写进了 `plan.md`；耗时超过 2 分钟的原因写进报告。构建本身坏了、修不好时，把输出如实写进报告。

## 6. 建 UI token（有界面时）

读 `references/ui-tokens.md`，按其中的步骤完成。没有界面时跳过；之后加了前端，重跑本 skill 即可补上。

完成条件：`references/ui-tokens.md` 末尾的完成条件都满足。

## 7. 验证

运行 `python3 <skill 目录>/scripts/check_harness.py <repo> --check-cmd "<检查命令>" --expect-output "<检查实际执行时一定会打印的正则>"`，修到输出 `OK`。有界面时为每个代码 token 文件加一个 `--tokens <文件>`；词表不是 `GLOSSARY.md` 或 `CONTEXT.md` 时加 `--glossary <文件>`；检查可能超过 10 分钟时加 `--timeout <秒>`。`note:` 开头的行逐条判断。

已有代码时再做一次定位测试。先从词表挑两个词，各写一条只用业务词描述、不提文件名和标识符的需求，把需求和正确的文件记进 `plan.md`。然后在全新上下文里启动一个子 agent（不支持子 agent 的工具，请用户在新会话里跑），prompt 只给仓库路径和这两条需求，要求它找出主要要改的文件、只读不改，最后说明第一次定位到主文件之前搜了几次（任何一次搜索或读文件都算一次，命令出错重跑不算）。结果写进 `plan.md`。它找错或超过 5 次时，修正词表或语义地图后再测一次。

完成条件：脚本输出 `OK`；已有代码时，两条需求都在 5 次内定位到了正确的文件，或未通过的情况已写进报告。

## 8. 报告

告诉用户：

- 分支，以及新建和改动的文件；
- 已有 harness 的优化结果：删减或迁移的每条事实和去向，来自 `plan.md`；
- 测试精简前后对比：测试文件数、测试行数、测试与源码的行数比、默认检查耗时，以及保留了哪些、为什么；审计发现的高风险测试缺口；
- 检查命令和它排除的历史失败、没跑的命令和原因；定位测试结果；
- 请用户确认的词条和设计决定；词表要深入打磨时，可以用 domain-modeling skill；
- 改动还没提交，请用户审查 diff。

最后提醒一句：之后 agent 反复犯同一个错时，能写成检查就写成检查，不能的再往 `AGENTS.md` 补一句。

完成条件：报告覆盖以上各项，每条被删减的事实都有交代。
