# 写 skill 的原则

起草和修改时查阅。每节先给规则，再给理由和例子。例子大多取自 mattpocock/skills 和 Anthropic 的 skill-creator。

总纲：依循性取决于两个量，**同时要背的约束有多少**，以及**从读到说明到执行它，中间隔了多少内容**。字数本身不是问题。下面各节都在压这两个量：能检查的交给脚本，要判断的放进短会话并写清完成条件，跨步骤的状态存进文件。规则只在观察到真实失败后才加，每次只补一句。拿不准时，选让这两个量更小的写法。

## 1. 调用方式

| | 用户手动调用 | 模型自动调用 |
| --- | --- | --- |
| 什么时候选 | 只在人想用时才跑：大流程、有副作用的操作、个人习惯 | agent 干活中途应该自己想到它，或者别的 skill 要调用它 |
| frontmatter | `disable-model-invocation: true` | 不写这一项 |
| description | 写给人看的一行摘要，像命令菜单里的一项，不写触发词 | 写给模型看：它是什么，加上每个触发分支 |
| 代价 | 不占上下文，但人得记得它存在 | 每一轮都常驻上下文 |

判断标准是"模型主动调用它有没有用"。能被复用是拆出 skill 的理由，不是判断调用方式的标准。

手动调用的 skill 不能被别的 skill 调用。某一步的前置条件是一个手动 skill 时，写成"告诉用户去运行 `/xxx`"。

手动 skill 多到记不住时，做一个路由 skill（例如 Matt 的 ask-matt），列出各个 skill 和各自的使用时机。路由在推荐之前要先读目标 skill 的 `SKILL.md`，不要相信自己写的摘要。

## 2. description

description 是模型决定是否调用一个 skill 的主要依据，而且每一轮都在上下文里。

- **先写它是什么，再写每个触发分支。** "什么时候用"的信息全部放在 description（或 `when_to_use`）里，正文不再重复。
- **覆盖每个真正不同的分支，包括用户没点名但明显需要的情况。** 模型容易漏用 skill，所以分支要写全，比如"用户说页面看起来像 AI 做的"也是"做页面"的一个分支。
- **同一分支的同义词合并成一个。** build、design、polish、restyle 如果指的是同一件事，只写一个。分支写全和同义词合并并不矛盾：要多的是分支，不是近义词。
- **触发分支可以带几句用户原话**（`Use when the user says "…"`），只带模型从意思上联想不到的：团队内部叫法、自造词、容易和别的 skill 混淆的说法。同一件事的几种说法只留一种。只在 Claude Code 里用的 skill，这些原话也可以放进 `when_to_use` 字段（拼在 description 后面，两者合计 1536 字符）；要给 Codex 等其他工具用的，继续写在 description 里。
- **关键词放最前面。**
- **不写正文已经讲清楚的身份介绍。**
- **"它是什么"用几个词点出这件事，不写成任务说明。** 参数、格式、规则（邮箱、分几块、列几个目录）属于正文。写进 description 的话，它读起来就成了一段完整的 prompt；改一个参数还得同时改两处。对照：
  - 写成 prompt 的：`把当前仓库最近 7 天我自己（me@example.com）的 commit 整理成中文 markdown 周报，分新功能、修复、重构、其他四块，末尾列改动最多的三个目录。`
  - 手动调用的：`整理本周自己的 commit，生成中文周报。`
  - 模型自动调用的：`整理一段时间内的 git commit，生成中文周报。Use when the user asks for a weekly report or a summary of this week's commits.`

示例（tdd）：`Test-driven development. Use when the user wants to build features or fix bugs test-first, mentions "red-green-refactor", or wants integration tests.`

模型只在自己不容易直接完成的任务上调用 skill，"读一下这个 PDF"这类一步就能做完的请求，description 写得再好也未必触发。所以要优化触发率时，测试用的提示要足够具体、有一定复杂度。skill-creator 有现成的 description 优化循环。

## 3. 粒度与会话

- **一个 skill 只做一件事。** 例：Matt 的 grilling（333 词）是一个最小单元，grill-me 只有一句"调用 grilling"，wayfinder 和 grill-with-docs 也都调用它。
- **一次运行放进一个短会话。** 说明在会话开头读过一次，后面跟着几十万 token 的工作，它就被淹没了。例：wayfinder 每个会话最多解决一个工单；主流程每做一张工单前先 `/clear`。
- **大约 15 万 token 以内是 smart zone**，模型推理还清醒。快到时在阶段边界压缩上下文，不要硬撑。
- **什么时候按阶段拆：** 后面的步骤会诱使 agent 草草做完前面的步骤时就拆。先试着把完成标准写得更具体；不行再拆。拆开要跨越真正的上下文边界才有用：交接文档、新会话或子 agent。同一会话里接着调用另一个 skill，不会把后面的步骤挪出视野。
- **什么时候按调用方式拆：** 某部分有自己独立的触发词，或者要被别的 skill 调用时。

反例：design-taste-frontend 把盘点、定方向、构建、检测、评审、动效、汇报全放在一个 30–45 分钟、几十万 token 的会话里。有脚本检查的规则执行得很彻底，靠判断的创意和质量在没见过的需求上却输给了不用 skill 的基线（6.9 对 7.9）。

## 4. 结构与渐进披露

正文里只有两种内容：**步骤**（按顺序做的事）和**参考**（规则、定义、事实，需要时查）。

skill 分三层加载：

1. 名称和 description：一直在上下文里，约 100 词；
2. `SKILL.md` 正文：触发时加载，最好在 500 行以内；
3. 附带资源：按需加载，数量不限。脚本可以直接运行，不必读进上下文。

```
skill-name/
├── SKILL.md        步骤和每个分支都要用的参考
├── references/     只有部分分支用到的参考，按需读
├── scripts/        确定性、重复性的工作
└── assets/         产出要用的模板、图标、字体
```

- **每个分支都要用的写进正文；只有部分分支用到的挪进 `references/`。** 正文里用一句话指过去，写清什么情况下去读。挪得太少，正文臃肿，步骤被参考淹没；挪得太多，agent 需要的东西被藏起来。
- **一个 skill 支持多个领域或框架时，按变体分文件**（例如 `references/aws.md`、`gcp.md`），agent 只读相关的那个。
- **同一概念放在同一个标题下**：定义、规则、注意事项放在一起，不要散落各处。
- **每个意思只写一处。** 写在多处会让它显得比实际更重要，改的时候也容易漏改。
- **长不怕，乱才怕。** Matt 的 code-review 有 1094 词，一半是 12 条坏味道清单，模型会逐条比对。平铺、按需查的参考写长也没问题。
- **超过 300 行的参考文件，开头放目录。**

## 5. 完成标准

每一步结尾写一个完成条件，满足两点：

- **能分辨做完和没做完。** "理解清楚了"不行；"frontier 为空，并且用户确认达成共识"可以（grilling）。标准含糊时，agent 容易在没真正做完时就收尾，因为它看得见后面还有步骤在等。
- **要求足够彻底。** "列出改动"不如"每个修改过的模型都有交代"。要求高了，agent 会自己去做该做的深挖。

技巧：

- **早失败。** code-review 第 1 步先确认比较基准能解析、diff 不为空，不让错误流进后面两个并行的子 agent。
- **能用脚本判断的，写成"某命令输出 X"。** 比如"`grep -n '—' out.md` 结果为空"，比"确认没有用破折号"可靠。
- **把模型会猜错的地方写死。** 比如 handoff 写明临时目录是 `$TMPDIR`，否则 `/tmp`，"让 agent 不再猜"。

## 6. 状态落成文件

跨步骤、跨会话要用的结论，写进文件，不留在模型的记忆里：spec、ticket、`GLOSSARY.md`、ADR、handoff 文档、issue。这样后续步骤能读到，人也能检查，"做没做完"也就成了可以核对的事。

索引只做索引：例如 wayfinder 的地图只给每个决策写一行概要加链接，决策内容只存在对应的工单里。

## 7. 措辞

- **用祈使句。**
- **说明理由，不靠大写的 MUST。** 模型懂了为什么，就能推广到没写到的情况。发现自己在写全大写的 ALWAYS 或 NEVER 时，换成解释。
- **用模型已经认识的概念词**，例如 seam、tracer bullet、red、frontier、fog of war、design tree。一个词就能调动模型已有的先验，比用一段话去定义便宜。自造词要给出清楚的定义，它不会自带先验。同一个词在 prompt、文档、代码里一致使用，触发也更可靠。
- **删掉模型默认就会做的句子**，整句删。词太弱、压不住默认行为时（比如 "be thorough"），换更强的词（比如 "relentless"），不要多加句子。
- **不复述环境里能查到的东西**（package.json、配置、目录结构、`--help`）。要写的是查不到的：未成文的约定、选择背后的原因、配置里看不出的坑。
- **固定格式就给模板**，比如"报告必须用这个结构"再跟一段骨架。**需要示例时给输入和输出的对照**，示例只示范正确的写法；要拦的写法放进审查清单（§8）。
- **写得通用。** 不要只围着某几个具体例子写，skill 会被用在大量没见过的提示上。

## 8. 压制规则

写"不要做 X"反而让 X 更容易出现，这就是粉色大象问题（心理学上叫白熊效应）。被禁的词一旦写进上下文，就被激活、可能被复制出来，而模型对"不"字的处理偏弱。禁令越多越细、离执行点越远、配的错误示例越多，这个效应越明显。

写提示词时：

- 说要做什么："不要用破折号"改成"句子用逗号、冒号或句号连接"。
- 非禁不可，就配替代做法，并把替代做法放在后面。
- 不复述、不示范被禁的东西；讲清理由；能给白名单（模板、枚举）就不给黑名单。

确实要压制时，禁令放在检查环节，不放在生成环节。按强度从高到低：

| 手段 | 适用 | 例子 |
| --- | --- | --- |
| 1. 让它做不到：权限、hook、结构化输出加 enum | 后果严重的操作 | `permissions.deny`；git-guardrails 用 hook 拦截 `git push` |
| 2. 用脚本检查，不过就重来 | 机械性规则 | lint、`grep`、design-taste-frontend 的 `inspect.mjs` |
| 3. 另开审查子 agent：全新上下文，附完整禁令清单 | 需要判断的规则 | code-review 的 Standards 子 agent |
| 4. 交付前过检查清单：条目写成命令或可观察的结果 | 兜底 | `grep -n '—'` 结果为空 |

第 3 层有效，是因为写作方只看到正面要求，审查方拿着禁令清单专门找问题，两边互不干扰。

各层的成本不同，选层时要算进去。写在被生成的 skill 里的检查，成本会乘以运行次数：脚本几乎不花钱；另开审查子 agent 每次大约要多花一分钟和一两万 token。所以优先用第 2 层；只有同时满足两个条件时才用第 3 层：规则**必须靠判断、写不成脚本**，并且**出错的代价高**（例如引用造假、对外发布的内容）。风格类、出错代价低的规则，用第 4 层的检查清单兜底就够了。选哪一层可以按 Matt 的这句话判断："Mechanical mistakes become deterministic checks; judgement calls become coding standards."（机械性错误变成确定性检查，需要判断的问题变成编码规范。）

## 9. 组合其他 skill 和派发子 agent

- **调用其他 skill 写成显式工具调用**：`Call the Skill tool with "tdd"`。只在正文里写 `/tdd`，模型未必会把它当成要执行的命令。
- **一步要用两个 skill 时**，写"调用两次 Skill 工具，分别是 X 和 Y"。写成"用 X 和 Y 调用"，读起来像一次调用。
- **共享的参考放在拥有它的那个 skill 里**，其他 skill 通过调用它来获得，不跨目录链接文件。
- **派子 agent 时，写明从全新上下文启动**，不 fork 父对话。有些工具（例如 Codex）默认会 fork，而子 agent 的价值就在于干净的上下文。子 agent 看不到父对话，它需要的材料要完整写进 prompt。

## 10. 篇幅参考

Matt 的 skill 的分布：

| 字数 | 类型 | 例子 |
| --- | --- | --- |
| < 100 | 包装、快捷指令 | grill-me、wait-what、implement |
| 100–600 | 单一原语 | research、handoff、grilling、tdd |
| 900–1100 | 带一组平铺规则的流程 | code-review、triage |
| ~2000 | 路由，或需要定义状态模型的大流程（手动调用） | ask-matt、wayfinder |

超过 2000 词时先查三件事：有没有重复？有没有只给部分分支用、该挪出去的内容？是不是该拆成两个 skill 或两个会话？

## 11. 测试与迭代

**发布前**：写 2–3 个真实用户会说的提示，分别在带 skill 和不带 skill（改写时用旧版本）的条件下各跑一次，让用户看产出给反馈。能客观核对的产出（文件转换、数据提取、固定流程）适合写断言；写作风格、设计这类主观产出，靠人看。skill-creator 有完整的工具链。

按反馈修改时：

- 推广，不迁就个例；遇到顽固问题，试试换一个比喻或换一种工作方式，而不是加更死的规矩。
- 读运行记录，不只看最终产出。让 agent 白白绕路的段落就删掉。
- 几次运行都各自写了相似的辅助脚本，就把它放进 `scripts/`。

**发布后**：只按观察到的真实失败修改。记录跑了什么、skill 做了什么、本来期望什么；"如果……会更好"这类假设不改。每次修改小而具体，通常只补一句。例：

- grilling：问题的措辞要让回答"是"就等于接受推荐答案（#706）
- implement：开工前先读出工单标题，引用有歧义时就问（#700）
- ask-matt：推荐前先读目标 skill 的 `SKILL.md`（#1194）

定期删减：不再相关的、过时的、模型默认就会做的句子，及时删掉，别让它们越积越多。

## 12. 不出意外

skill 做的事，用户读描述时就应该能预料到。不写恶意代码、漏洞利用、数据外传，也不写误导用户或帮助未授权访问的 skill。角色扮演这类明确告知用户的用途没有问题。
