# skill 审查清单

给审查子 agent 用。逐条对照草稿，每发现一处问题：引用原文，标出属于哪一条，判定是"硬性问题"还是"需要判断的问题"，并写出改法。没有问题的条目不用列。报告控制在 500 字以内，按严重程度排序。

## description 与调用方式

1. 只在人想用时才跑的 skill（大流程、有副作用、个人习惯），却没有设置 `disable-model-invocation: true`；或者手动调用的 skill，description 里还留着触发词。
2. description 没先说它是什么，或者漏了真正不同的触发分支，包括用户没点名但明显需要的情况。
3. description 用一串同义词重复描述同一个分支。
4. description 复述了正文已经讲清楚的身份介绍，或者正文里又写了一遍"什么时候用"。
5. description 写成了任务说明：带着参数、格式、规则（具体邮箱、分几块、列几项），读起来像一段完整的 prompt，而不是几个词点出这件事加上触发分支。

## 粒度与会话

6. 一个 skill 做了几件可以各自独立触发的事。
7. 一次运行明显放不进一个短会话，或者后面的步骤会诱使 agent 草草做完前面的步骤，却没有按阶段拆开、用文件交接。
8. 重复写了已有 skill 能提供的内容，没有用 `Call the Skill tool with "<name>"` 去组合。

## 结构

9. 只有部分分支用到的大段参考留在正文里，把步骤淹没了。
10. agent 每次都要用的内容被挪进了 `references/`，或者指向 `references/` 的指引没写明什么时候读。
11. 同一个意思写在多处。
12. 同一个概念的定义、规则、注意事项散落在不同标题下。
13. `SKILL.md` 超过 500 行，或者超过 300 行的参考文件开头没有目录。

## 步骤与完成标准

14. 某一步没有完成条件，或者完成条件含糊到分不清做完和没做完（"理解清楚了""确认质量"）。
15. 完成条件要求太低，agent 会浅尝辄止（"列出改动"，而不是"每个改动都有交代"）。
16. 跨步骤要用的结论只留在"笔记"或模型记忆里，没有落成文件。
17. 能用脚本或命令判断的检查，写成了让模型自己"确认"。
18. 确定性、重复性的工作（固定格式转换、校验）没有放进 `scripts/`，而是让模型每次自己写。

## 措辞

19. 禁令没有配替代做法，或者大段描写、示范了被禁止的写法。
20. 需要压制、而且能写成脚本检查的规则，只写在提示词里。
21. 必须靠判断、出错代价又高的压制规则（引用造假、对外发布的内容）挤在写作步骤里，没有交给独立审查环节；或者反过来，风格类、出错代价低的规则每次运行都另开审查子 agent，用检查清单兜底就够了。
22. 用全大写的 MUST、ALWAYS、NEVER 代替解释理由。
23. 有模型默认就会做的句子，或者"be thorough"这类压不住默认行为的弱词。
24. 复述了环境里一条命令或一个文件就能查到的信息。
25. 用一段话描述一个概念，而模型本来就认识表达它的现成词；或者自造了词却没有定义。
26. 内容只围着某几个具体例子写，换个提示就用不上。

## 组合与子 agent

27. 调用其他 skill 只写了 `/name`，没有写成 `Call the Skill tool with "name"`；或者把两个 skill 写成一次调用。
28. 把手动调用的 skill 写成 Skill 工具调用（别的 skill 调不到它），而不是"告诉用户去运行 `/name`"。
29. 派发子 agent 时没写明从全新上下文启动，或者没把子 agent 需要的材料完整写进 prompt。

## 安全

30. skill 实际做的事超出用户读 description 时能预料的范围，或者包含恶意代码、数据外传、未授权访问。

## 报告格式

```
## 硬性问题
- [条目号] "<引用原文>" → <改法>

## 需要判断的问题
- [条目号] "<引用原文>" → <改法>（为什么值得改）

## 总结
硬性 N 条，判断 M 条。最该先改的三处：……
```
